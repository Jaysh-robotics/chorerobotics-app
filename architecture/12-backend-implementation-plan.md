### Step 3: Firestore Security Rules -- Phase F1

Deploy initial rules that only cover the `users` collection:

```javascript
rules_version = '2';
service cloud.firestore {
  match /databases/{database}/documents {
    function isAuthenticated() {
      return request.auth != null;
    }
    function isUser(userId) {
      return isAuthenticated() && request.auth.uid == userId;
    }

    match /users/{userId} {
      allow read: if isUser(userId);
      allow create: if isUser(userId) &&
        request.resource.data.keys().hasAll(['email', 'displayName', 'createdAt']) &&
        request.resource.data.email == request.auth.token.email;
      allow update: if isUser(userId) &&
        !request.resource.data.diff(resource.data).affectedKeys()
          .hasAny(['email', 'createdAt']);
      allow delete: if false;
    }

    // Deny everything else
    match /{document=**} {
      allow read, write: if false;
    }
  }
}
```

```
    v
Robot downloads updated zone set if version mismatch
```

```dart
class TelemetryService {
  final _rtdb = FirebaseDatabase.instance;

  // Listen to live telemetry from Realtime Database
  // Used when robot is cloud-connected (no local BLE/WiFi)
  Stream<TelemetryModel> watchTelemetry(String robotId) {
    return _rtdb
      .ref('robots/$robotId/telemetry')
      .onValue
      .map((event) => TelemetryModel.fromRtdb(event.snapshot.value));
  }

  // Listen to individual field (battery screen only needs battery_pct)
  Stream<double> watchBatteryPct(String robotId) {
    return _rtdb
      .ref('robots/$robotId/telemetry/battery_pct')
      .onValue
      .map((event) => (event.snapshot.value as num).toDouble());
  }
}
```

```dart
class NotificationService {
  static Future<void> initialize() async {
    // Request permissions (iOS)
    final messaging = FirebaseMessaging.instance;
    await messaging.requestPermission(
      alert: true,
      badge: true,
      sound: true,
    );

    // Get and store FCM token
    final token = await messaging.getToken();
    if (token != null) {
      await FcmTokenService.registerToken(token);
    }

    // Listen for token refresh
    messaging.onTokenRefresh.listen(FcmTokenService.registerToken);

    // Foreground message handler
    FirebaseMessaging.onMessage.listen(_handleForegroundMessage);

    // Background message handler (must be top-level function)
    FirebaseMessaging.onBackgroundMessage(_firebaseBackgroundHandler);

    // Handle notification tap (app opened from notification)
    FirebaseMessaging.onMessageOpenedApp.listen(_handleNotificationTap);
  }
}
```

```dart
class FirmwareService {
  Future<FirmwareModel?> checkForUpdate(String currentVersion, String model) async {
    final snapshot = await FirebaseFirestore.instance
      .collection('firmware')
      .where('targetModels', arrayContains: model)
      .where('releaseChannel', isEqualTo: 'stable')
      .where('rolloutStage', isEqualTo: 'full')
      .orderBy('versionCode', descending: true)
      .limit(1)
      .get();

    if (snapshot.docs.isEmpty) return null;

    final latest = FirmwareModel.fromFirestore(snapshot.docs.first);
    if (latest.versionCode > _parseVersionCode(currentVersion)) {
      return latest;
    }
    return null;
  }
}
```

### Data Formats

**Drive Command (4 bytes packed, little-endian):**

```
Byte 0: linear_x  (int8, -127 to +127) - forward/backward speed
Byte 1: linear_y  (int8, -127 to +127) - left/right strafe (unused, reserved)
Byte 2: angular_z (int8, -127 to +127) - left/right rotation
Byte 3: flags     (uint8, bitfield)
         bit 0: blade_on
         bit 1: turbo_mode
         bit 2-7: reserved
```

Rationale: Packed bytes instead of JSON for drive commands because this characteristic is written at 30Hz. JSON parsing overhead at 30Hz adds measurable latency. 4 bytes fits in a single BLE write without fragmentation.

**Core Telemetry (20 bytes packed, little-endian):**

```
Bytes  0-1:  battery_pct      (uint16, 0-10000, divide by 100 for %)
Bytes  2-3:  battery_voltage   (uint16, millivolts, divide by 1000 for V)
Bytes  4-5:  speed_ms          (int16, mm/s, divide by 1000 for m/s)
Bytes  6-7:  heading_deg       (uint16, 0-35999, divide by 100 for degrees)
Byte   8:    state             (uint8, enum: 0=idle,1=working,2=charging,3=paused,4=error,5=estop,6=docked)
Byte   9:    signal_strength   (uint8, 0-4)
Byte  10:    rtk_status        (uint8, 0=none,1=single,2=float,3=fix)
Byte  11:    satellite_count   (uint8, 0-30)
Bytes 12-13: system_temp       (int16, centi-degrees, divide by 100 for C)
Bytes 14-15: battery_current   (int16, milliamps, negative=charging)
Bytes 16-17: battery_temp      (int16, centi-degrees)
Byte  18:    battery_health    (uint8, 0-100 percent)
Byte  19:    battery_cycles_hi (uint8, high byte of cycle count)
            -- cycle count = (byte19 << 8) | byte from extended telemetry
```

**GPS Position (12 bytes packed, little-endian):**

```
Bytes 0-3:  latitude    (int32, microdegrees, divide by 1,000,000)
Bytes 4-7:  longitude   (int32, microdegrees, divide by 1,000,000)
Bytes 8-9:  accuracy_cm (uint16, centimeters)
Bytes 10-11: reserved
```

**Motor Speeds (8 bytes packed, little-endian):**

```
Bytes 0-1: motor_fl_rpm (int16, signed RPM)
Bytes 2-3: motor_fr_rpm (int16, signed RPM)
Bytes 4-5: motor_rl_rpm (int16, signed RPM)
Bytes 6-7: motor_rr_rpm (int16, signed RPM)
```

### Pairing Flow

```
ROBOT STATE                           APP STATE
-----------                           ---------

1. Power on
   LED: White slow blink (1s/1s)
   BLE: Start advertising
   Name: "ChoreBot-XXXX" (last 4 of serial)

                                      2. App opens BLE scan screen
                                         App sees "ChoreBot-XXXX" in scan

3. App connects to GATT
   LED: White fast blink (300ms/300ms)
   Pairing State char: 1 (FOUND)

                                      4. App reads Serial Number characteristic
                                         App displays UUID for user to verify
                                         App reads Attachment Type characteristic

5. User taps "Pair This Robot"
   LED: White double blink
   Pairing State char: 2 (PAIRING)
   Robot generates 6-digit code
   Robot displays code on its screen/LEDs

                                      6. User reads code from robot
                                         User enters 6-digit code in app
                                         App writes code to Pairing Code characteristic

7. Robot receives code
   LED: White rapid blink (100ms/100ms)
   Pairing State char: 3 (VERIFYING)
   Robot compares entered code vs generated code

   IF MATCH:
     LED: Green 3 flashes then solid
     Pairing State char: 4 (SUCCESS)
     Pairing Result char: 1 (SUCCESS)
     Generate pairing token (32-char random)
     Write token to Pairing Token characteristic

                                      8. App reads Pairing Token
                                         App stores token locally (secure storage)
                                         App navigates to WiFi setup screen

   IF NO MATCH:
     LED: Red 3 flashes
     Pairing State char: 5 (FAILED)
     Pairing Result char: 2 (FAILED)
     After 3 seconds, return to state 0 (discoverable)
```

**Pairing Code Generation:**

```python
import secrets
code = f"{secrets.randbelow(1000000):06d}"  # "042917"
```

The code is displayed on the robot's screen (if available) or communicated via LED pattern (future). For MVP, the code is printed on a card included with the robot and pre-loaded during manufacturing.

**Pairing Token:**

```python
import secrets
token = secrets.token_hex(16)  # 32-character hex string
```

The pairing token serves dual purpose:
1. WebSocket authentication (included in WebSocket handshake)
2. Firebase pairing verification (written to Firestore during registration)

### LED Control During Pairing States

Integration with `led_pairing_spec.md`:

| Pairing State | LED State | Color | Pattern | Timing |
|---------------|-----------|-------|---------|--------|
| 0: Discoverable | 1 | White | Slow blink | 1s on / 1s off |
| 1: Found | 2 | White | Fast blink | 300ms on / 300ms off |
| 2: Pairing | 3 | White | Double blink | 100ms on, 100ms off, 100ms on, 700ms off |
| 3: Awaiting Code | 4 | White | Solid ON | Constant |
| 4: Verifying | 5 | White | Rapid blink | 100ms on / 100ms off |
| 5: Success | 6 | Green | 3 flashes then solid | 150ms on/off x3, then constant |
| 6: WiFi Setup | 7 | Green | Slow blink | 2s on / 0.5s off |
| 7: Complete | 8 | Green | Solid ON | Constant |
| 8: Failed | 9 | Red | 3 flashes then off | 500ms on/off x3, then restart |
| E-STOP | 10 | Red | Rapid flash | 200ms on / 200ms off, non-stop |

E-Stop (state 10) overrides ALL other LED states immediately.

### Authentication

The WebSocket handshake includes the pairing token for authentication:

```
GET /ws HTTP/1.1
Host: chorerobot-XXXX.local:8765
Upgrade: websocket
Connection: Upgrade
Sec-WebSocket-Key: <key>
X-Pairing-Token: <32-char hex token from BLE pairing>
```

The server validates `X-Pairing-Token` against its stored token. If the token does not match, the server responds with HTTP 401 and closes the connection.

### Message Protocol

All WebSocket messages are JSON text frames with a required `type` field.


- `type` (string, required): Message type identifier
- `id` (string, required): Unique message ID (UUID v4) for correlation
- `timestamp` (integer, required): Unix milliseconds
- `payload` (object, required): Type-specific data

### Heartbeat / Keepalive

- The app sends a `ping` message every 5 seconds
- The robot responds with `pong` within 1 second
- If the app misses 3 consecutive pongs (15 seconds), it considers the WebSocket disconnected
- The robot considers the app disconnected if it receives no messages for 15 seconds
- On disconnect, the robot follows the connection-loss safety protocol:
  - 0-10s: Continue current task
  - 10-20s: Pause task, hold position
  - 20-30s: Return to dock
  - 30s+: Emergency stop

## B4: LED Controller

### Hardware Configuration

- LED Strip: WS2812B (NeoPixel-compatible) addressable RGB strip
- LED Count: 12 LEDs (front-mounted horizontal bar)

- Power: 5V from robot power supply (not USB -- WS2812B needs 5V logic)

### LED States Implementation

| State ID | Name | Color RGB | Pattern | Implementation |
|----------|------|-----------|---------|----------------|
| 0 | OFF | (0,0,0) | All off | `set_all(0,0,0)` |
| 1 | Discoverable | (255,255,255) | Slow blink | 1000ms on, 1000ms off |
| 2 | Found | (255,255,255) | Fast blink | 300ms on, 300ms off |
| 3 | Pairing | (255,255,255) | Double blink | 100ms on, 100ms off, 100ms on, 700ms off |
| 4 | Awaiting Code | (255,255,255) | Solid | Always on |
| 5 | Verifying | (255,255,255) | Rapid blink | 100ms on, 100ms off |
| 6 | Success | (0,255,0) | 3 flashes then solid | 150ms on/off x3, then solid |
| 7 | WiFi Setup | (0,255,0) | Slow blink | 2000ms on, 500ms off |
| 8 | Complete | (0,255,0) | Solid | Always on |
| 9 | Failed | (255,0,0) | 3 flashes then off | 500ms on/off x3, then transition to state 1 |
| 10 | E-STOP | (255,0,0) | Rapid flash | 200ms on, 200ms off, non-stop |

### Integration with Pairing State Machine

The LED controller subscribes to pairing state changes from the BLE GATT server:

```python
class LedController:
    def on_pairing_state_changed(self, new_state: int):
        """Called by BLE pairing module when state changes."""
        if self._estop_active:
            return  # E-STOP overrides all states
        self._set_led_state(new_state)

    def on_estop(self, active: bool):
        """E-STOP has highest priority, overrides any LED state."""
        self._estop_active = active
        if active:
            self._set_led_state(10)  # Red rapid flash
        else:
            self._set_led_state(self._last_normal_state)
```

## Protocol Summary

### Command Types (App to Robot)

| Command | BLE Characteristic | WebSocket Type | Firebase Command | Priority | Latency Requirement |
|---------|-------------------|----------------|-----------------|----------|-------------------|
| Drive (joystick) | `CHOR0301` (4-byte packed) | `drive_command` | N/A (never cloud) | Normal | < 33ms (30Hz) |
| Task Start | `CHOR0302` (JSON) | `task_start` | `start_task` | Normal | < 5s |
| Task Stop | `CHOR0302` (JSON) | `task_stop` | `stop_task` | High | < 1s |
| Task Pause | `CHOR0302` (JSON) | `task_pause` | `pause_task` | Normal | < 1s |
| Task Resume | `CHOR0302` (JSON) | `task_resume` | `resume_task` | Normal | < 5s |

|-----------|-------------------|----------------|---------------|------------|-------------|-------------|

### E-Stop Protocol

E-Stop is the highest-priority safety operation. It is sent on ALL available channels simultaneously.

**Multi-Channel E-Stop:**

```
User long-presses E-Stop button (>500ms hold required)
    |
    +--> BLE: Write 0x01 to CHOR0303 characteristic
    |         Latency: < 50ms
    |         Priority: HIGHEST
    |
    +--> WiFi: Send {"type":"estop"} WebSocket message
    |         Latency: < 50ms
    |         Priority: HIGHEST
    |
    +--> Firebase: Create command {type:"estop"} in Firestore
              Latency: 200-2000ms
              Priority: LAST RESORT

Robot processes FIRST arriving E-Stop:
    1. Hardware motor controller receives stop signal
    2. All motors stop via hardware interrupt (not software)
    3. Blade motor stops via separate hardware relay
    4. Robot state set to "estop"
    5. LED set to state 10 (Red rapid flash)
    6. Robot acknowledges E-Stop on all channels
    7. Robot rejects ALL commands except "estop_clear"
```

**E-Stop Clear Protocol:**

```
User initiates E-Stop clear in app:
    1. App shows safety checklist:
       [ ] I have visually inspected the robot
       [ ] The area around the robot is clear
       [ ] I understand the robot will resume accepting commands
    2. User checks all boxes and taps "Clear E-Stop"
    3. App sends clear command with confirmation code "CLEAR-ESTOP"
    4. Robot runs self-diagnostics (5-10 seconds):
       - Check all motor controllers respond
       - Check blade motor controller responds
       - Check all sensors are reporting
       - Check battery level is above minimum
    5. If diagnostics pass:
       - Robot state changes from "estop" to "idle"
       - LED returns to previous state
       - Robot resumes accepting commands
    6. If diagnostics fail:
       - Robot stays in "estop" state
       - Robot reports specific failure via alert
       - App shows "Cannot clear E-Stop: [reason]"
```

### BLE vs WiFi vs Cloud Decision Matrix

```
IF BLE connected AND command is safety-critical (E-Stop, blade):
    → Send via BLE (lowest latency)

IF BLE connected AND command is drive (joystick):
    → Send via BLE (packed bytes, 30Hz)

IF WiFi connected AND command is NOT drive:
    → Send via WiFi (higher bandwidth, JSON)

IF WiFi connected AND command is drive:
    → Send via WiFi (JSON, 30Hz -- acceptable latency)

IF only Cloud connected AND command is task-level:
    → Send via Firebase command (start_task, stop_task, dock)

IF only Cloud connected AND command is drive:
    → BLOCK -- manual control requires local connection
    → Show "Manual control requires local connection to robot"

IF only Cloud connected AND command is blade toggle:
    → BLOCK -- blade control requires local connection (safety)

IF only Cloud connected AND command is E-Stop:
    → Send via Firebase (last resort, 200-2000ms latency)
    → Also show warning: "E-Stop sent via cloud. Verify robot has stopped."
```
